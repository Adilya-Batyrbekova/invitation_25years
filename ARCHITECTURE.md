## Recommended stack and rationale

Use React with TypeScript, Vite and plain CSS for the guest site and a separately loaded administrator area. Publish a static build on a suitable free host; GitHub Pages uses the owner-authorized public repository and a project-prefixed static build (see Costs and operations). Use Supabase Postgres and Auth for guest data and browser ownership, and Edge Functions for the owner Telegram webhook. Use local files for site editing and Pages for the resulting public snapshot. Use the official Supabase JavaScript client. No component library, custom application server, SSR, separate CMS or CRM is justified now.

React supports the stateful forms, gift filters and content editor without duplicating interaction logic. TypeScript checks data contracts. Vite builds static files suitable for Pages. SSR and search-oriented rendering are not required. Supabase is necessary because Pages does not provide a writable database or server runtime, while reservations and wishes must be shared and access-controlled. Owner reports read from Postgres through the Telegram webhook.

This is sufficient for one event and later copies. It deliberately does not build a multi-customer service. Plain static files alone would not meet persistence and authorization requirements. The deferred alternative below is recorded at the owner's request, not selected for implementation.

The draft installs React/React DOM 19.3.1, TypeScript 6.0.3 and Vite 8.3.5; the exact resolved dependency set is in `invitation/package-lock.json`. Use Node 24 (verified bundled runtime 24.22.1). System Node 20.17.0 is incompatible with the selected tooling; invoking the system npm shim used that old runtime despite PATH ordering. Use the documented explicit bundled runtime launcher on this workstation.

GSAP 3.15.0 and `@gsap/react` 2.1.2 handle scoped reveal, calendar and envelope sequences with cleanup. No Lenis, Three.js or component library is installed. Native scrolling is retained. Cursor ribbons use Canvas 2D and are disabled for coarse pointers/reduced motion. Music is a quiet original Web Audio note sequence, not copied reference audio. Phosphor React 2.1.10 supplies UI icons. Fontsource supplies self-hosted Great Vibes (script accents) and Nunito (rounded body text, 400/600). They replace Pacifico/Neucha/Literata following the owner's supplied font shortlist. Both Cyrillic and Latin subsets are bundled locally; the font change introduces no runtime service. Official family references: [Great Vibes](https://fonts.google.com/specimen/Great+Vibes), [Nunito](https://fonts.google.com/specimen/Nunito). Generated painted illustrations are local WebP files. All provisional shared visual values live in `src/styles/site.css`; this does not constitute owner design approval.

The owner authorized replacing SBOL Typograph on 2026-10-29. The pinned MIT-licensed Typograf 7.8.0 runs locally through src/lib/typography.ts; see [provenance](invitation/src/lib/vendor/PROVENANCE.md). It provides punctuation, quote, spacing and nonbreaking-space rules while preserving editable source copy. Telephone normalization is disabled, and intentional ё remains in source rather than a dictionary rewrite. No text is sent to a remote typography service. Every display string continues through t(), P or Title, and future adapters must preserve that plain-text boundary. The old vendor implementation is removed from the current source/build without rewriting historical commits. The MIT license ships with the public build.

## Deferred alternative: Payload with PostgreSQL

On 2026-10-27 the owner asked to record Payload with PostgreSQL as an available alternative only. The current recommendation above remains unchanged; this is not authorization to install Payload, migrate data or replace the architecture.

Payload provides a configurable administrator interface, authentication, access control and APIs, and officially supports PostgreSQL. It could reduce custom content-management UI work and support later reuse. Guest browser ownership, wish editing permissions and transactional gift reservation behavior would still require project-specific implementation and tests.

Payload requires a server runtime compatible with its Next.js deployment; it cannot run on static GitHub Pages. Adoption would require separate hosting for Payload or moving the combined application to suitable hosting, plus database and persistent image storage. A complete zero-cost deployment and its operating limits have not been validated. Reconsider only after checking these costs, hosting compatibility and maintenance implications; update this architecture and related documents if adoption is later decided. PostgreSQL is already part of the current Supabase recommendation, so the main alternative is the administrator/backend layer.

Official references reviewed during the discussion: [Payload overview](https://payloadcms.com/docs/getting-started/what-is-payload), [PostgreSQL adapter](https://payloadcms.com/docs/database/postgres), and [deployment requirements](https://payloadcms.com/docs/production/deployment).

## Data and permissions

| Planned record | Contents | Access |
| --- | --- | --- |
| `site_content` | Structured editable texts, event details, contact and Telegram links, conversion rate/date | Public read of published fields; admin write |
| `personal_entries` | Owner-provided stories, captions, image references, order | Public read of published entries; admin write |
| `gifts` | Public catalog fields and publication state | Public published read; admin write |
| `attendance` | Browser owner ID, guest name, yes/no, timestamps | Submitter insert through validated operation; admin read/correct; no guest update |
| `wishes` | Owner ID, public name/text, timestamps | Public projection; author update; admin update/delete |
| `reservations` | Gift ID, owner ID, private guest name, timestamp | Validated claim/cancel operations; admin private read/correct |
| `admin_members` | Explicit administrator user IDs | Privileged setup only; no client self-assignment |

Public reads must expose only intended columns. Never publish reservation names or ownership identifiers through catalog payloads, views or error messages. Return public gift availability and a scoped own-reservation response separately from private reservation records. The administrator interface only reads reservation statuses. The underlying private table is inaccessible to application clients. No gift-association data belongs in Markdown or repository files.

Use a database unique constraint on reserved gift ID and a transactional claim operation to prevent double reservation. Cancellation checks the authenticated owner ID inside the database operation. Reject malformed values and invalid gifts on the backend. Use plain text for guest wishes; never render guest HTML. Record limits and enforce them consistently on the client and backend.

Enable row-level security on exposed tables. Audit view execution permissions and any security-definer function, its search path and grants; avoid elevated functions where policies suffice. Public availability endpoints must not bypass privacy accidentally. A hidden admin page is not authorization. Derive admin rights from protected membership, not client-controlled metadata. Privileged service keys stay outside the client build and repository; only publishable client configuration is shipped.

## Registration-free ownership

Create an anonymous Supabase Auth session when a guest first needs to submit or manage data. Retain the session in the browser using the supported client persistence mechanism. The server-issued user ID establishes ownership for database policies; IP and guest names do not. This is technical authentication without a guest registration form, email or identity verification.

The session is specific to browser storage and site origin. Private mode, cleared storage, a different browser/device or a domain change may lose access. Tell guests to contact the owner for corrections; do not offer unauthenticated ownership recovery by name. Losing a session does not delete the stored record. Attendance duplicate handling is best effort per session, not verified per human.

The local editor is restricted to loopback and runs outside Pages. Owner reports use the Telegram webhook and a server-side numeric account allowlist. The deployed legacy cloud editor used GitHub OAuth and protected database membership. Preserve its restrictions while the current Pages version depends on the legacy content path.

Public links can be forwarded. Anonymous writes need basic abuse controls: validate inputs, constrain text size, use submission throttling and evaluate the provider's recommended CAPTCHA protections. Select a free compatible challenge only if necessary; it must not add guest registration. Measure the chosen provider's rate limits against guests who may share the venue's network. Anonymous-account cleanup and database export must be documented before retirement.

## Owner content editor

The development-only /owner route uses a loopback Vite middleware to read and write an ignored local draft. The API checks the socket address, host, origin and explicit editor header. Draft writes use a temporary file and rename. The guest reader prefers the published static snapshot and falls back to the existing cloud content during transition. Development preview explicitly selects the saved draft. Editing does not require Supabase Auth. The prior cloud editor migration and policy fixture remain available for the deployed version.

The editor decodes source images in the browser and offers a visible crop with zoom and position controls. It encodes the chosen raster as PNG without lossy compression. Cropping and resizing change the raster by design. The longest output side is at most 1200 pixels. Publishing hashes asset bytes and copies referenced files before writing the snapshot. The original file is preserved by the filesystem.

The [gift reservation migration](supabase/migrations/202611070003_gift_reservations.sql) restricts reservation writes to scoped RPCs. The [registry migration](supabase/migrations/202611070004_gift_registry.sql) copies existing catalogue metadata and changes the claim RPC to check a private registry instead of the public content document. Keep the existing numeric IDs. Assign a fresh ID to each new gift and preserve it when editing or reordering cards. Retire registry entries without reusing their IDs or removing their bookings. A primary key limits each gift to one reservation. Cancellation checks ownership. The status RPC returns only gift IDs and caller ownership. The [SQL fixture](supabase/tests/gift_reservations.sql) exercises independent identities, duplicate claims, cancellation, denial of direct name access and booking preservation after registry edits.

The local preparation script emits a transaction to synchronize registry IDs, names, prices and bookability through a privileged database session. It never deletes a registry entry or a reservation. Apply the reviewed registry update before Pages exposes new IDs. The availability RPC marks missing or unavailable registry data as unavailable in the guest interface.

Personal and preferences snapshots can be prepared independently with their content-addressed images. Independent snapshots take precedence over the full snapshot and the cloud source for their respective sections. A full release must reconcile the independent files.

When the personal snapshot replaces fallback content, page motion reinitializes against the rendered cards so every story receives its stacking order. A story taller than the available viewport scrolls in document flow while the other stories retain sticky transitions. Both stories and small preferences repeat the lilac, yellow and blue palette. Explicit photo lists render exactly the selected assets, including built-in artwork. Empty lists render text-only stories.

Publish mode is enabled explicitly on the loopback editor. The owner authorizes a content-only commit and push by pressing Save and Publish. The server persists the draft first, verifies the Git destination, builds the selected section in a disposable checkout of the remote main branch, and pushes without force. It serializes publication jobs and checks the public snapshot before reporting it live. The Git credentials remain with the local process. Wishlist publication uses the existing owner GitHub OAuth account and a dedicated [database function](supabase/migrations/202611110001_publish_gifts.sql). After the local draft saves, the owner client uploads immutable gift photos to the existing Supabase image bucket. The function checks database administrator membership and updates the public gifts section and the private registry in one transaction. Retired IDs cannot be reused and reservation records are preserved. GitHub Pages reads the public catalogue through the existing Supabase fallback, so the wishlist needs no Git build per edit while that fallback is active. The [SQL fixture](supabase/tests/publish_gifts.sql) checks guest denial, retries, published order and reservation preservation.

Formatted preferences copy remains string-valued in the draft and published snapshot. A shared React renderer handles a limited set of paragraph, line break, emphasis and list markers. It applies the shared typography formatter to text fragments and does not interpret HTML.

The preferences snapshot stores ordered cards with stable IDs, descriptions, photos and disclosure entries. The editor and guest reader normalize the previous fixed topics to the same order and retain their content. The preparation script resolves photos at both card and entry levels. Automated publication checks that the target guest reader supports the card format before pushing.

The owner webhook supports three paginated reports plus wish edits, wish deletion and booking cancellation. It checks the Telegram secret header and the owner’s numeric sender and private chat IDs before any database request. Separate service-role-only RPCs limit reads to the report fields and writes to the three supported actions. Reports expose opaque record IDs for commands and omit giver names and ownership IDs. Cancellation targets a UUID generated for each booking, including after a rebooking. The owner menu uses Telegram callbacks and answers each callback through the Bot API. Setup preserves the existing registered webhook address and identifies the failed Telegram API step without exposing credentials. A ForceReply prompt stores only the wish ID and prompt message ID in a private, expiring, single-use row for the owner chat. The reply consumes that row and updates the wish in one transaction. The guest feed refreshes on focus, when made visible and every 30 seconds while visible. It edits and deletes wishes in a compact native modal. The owner-only delete policy for the anonymous guest session is enforced by Postgres RLS; guest clients receive only public wish fields. An isolated browser fixture supplies synthetic wishes and mixed gift availability without contacting the hosted database. The webhook replies with Telegram HTML and escapes dynamic text. Reports show a continuation command only when more results are available. Telegram delivery stays separate from guest submissions.
