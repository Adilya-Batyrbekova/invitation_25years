# Planned architecture

Status: React guest-page design draft implemented locally in `invitation/` on 2026-10-28; backend, administrator area, authentication and deployment remain planned. Product authority: [REQUIREMENTS.md](REQUIREMENTS.md).

## Recommended stack and rationale

Use React with TypeScript, Vite and plain CSS for the guest site and a separately loaded administrator area. Publish a static build on a suitable free host; GitHub Pages uses the owner-authorized public repository and a project-prefixed static build (see Costs and operations). Use Supabase Postgres, Auth and Storage for shared data, browser ownership, administrator login and administrator-uploaded site images. Use the official Supabase JavaScript client. No component library, custom application server, SSR, separate CMS or CRM is justified now.

React supports the stateful forms, gift filters and content editor without duplicating interaction logic. TypeScript checks data contracts. Vite builds static files suitable for Pages. SSR and search-oriented rendering are not required. Supabase is necessary because Pages does not provide a writable database or server runtime, while reservations, wishes and administrator updates must be shared and access-controlled. Postgres is behind the administrator tables; the owner does not need to operate it directly.

This is sufficient for one event and later copies. It deliberately does not build a multi-customer service. Plain static files alone would not meet persistence and authorization requirements. The deferred alternative below is recorded at the owner's request, not selected for implementation.

The draft installs React/React DOM 19.3.1, TypeScript 6.0.3 and Vite 8.3.5; the exact resolved dependency set is in `invitation/package-lock.json`. Use Node 24 (verified bundled runtime 24.22.1). System Node 20.17.0 is incompatible with the selected tooling; invoking the system npm shim used that old runtime despite PATH ordering. Use the documented explicit bundled runtime launcher on this workstation.

GSAP 3.15.0 and `@gsap/react` 2.1.2 handle scoped reveal, calendar and envelope sequences with cleanup. No Lenis, Three.js or component library is installed. Native scrolling is retained. Cursor ribbons use Canvas 2D and are disabled for coarse pointers/reduced motion. Music is a quiet original Web Audio note sequence, not copied reference audio. Phosphor React 2.1.10 supplies UI icons. Fontsource supplies self-hosted Great Vibes (script accents) and Nunito (rounded body text, 400/600). They replace Pacifico/Neucha/Literata following the owner's supplied font shortlist. Both Cyrillic and Latin subsets are bundled locally; the font change introduces no runtime service. Official family references: [Great Vibes](https://fonts.google.com/specimen/Great+Vibes), [Nunito](https://fonts.google.com/specimen/Nunito). Generated painted illustrations are local WebP files. All provisional shared visual values live in `src/styles/site.css`; this does not constitute owner design approval.

The owner authorized replacing SBOL Typograph on 2026-10-29. The pinned MIT-licensed Typograf 7.8.0 runs locally through src/lib/typography.ts; see [provenance](invitation/src/lib/vendor/PROVENANCE.md). It provides punctuation, quote, spacing and nonbreaking-space rules while preserving editable source copy. Telephone normalization is disabled, and intentional ё remains in source rather than a dictionary rewrite. No text is sent to a remote typography service. Every display string continues through t(), P or Title, and future adapters must preserve that plain-text boundary. The old vendor implementation is removed from the current source/build without rewriting historical commits. The MIT license ships with the public build.

### Visual reference implementation notes

The actual Style 1 / Style 2 images and concept canvas were inspected. Public scripts from the owner's five reference sites were examined through local Edge automation after the built-in browser failed with a sandbox helper error. Arbor uses GSAP clip-path reveals with `power2.inOut` and scroll-linked image movement; Ascension uses GSAP timelines and smoothed pointer motion; Emotion and Leopar use WebGL shader effects; Decathlon uses scroll-driven motion. The draft reuses these broad timing and reveal patterns, but does not claim shader or scene parity. The latest review restores individually rising, prefilled Great Vibes glyphs. `Title` imports the existing prepared glyph table and renders only filled SVG paths at their font advance/baseline metrics; there is no contour path or opacity tween on the fill. Glyph motion is 0.85 s with 0.045 s staggering, matching the earlier letter rhythm. `Words`/`P` retain body text reveals by word. Both pass source text through Typograph, preserve plain-text React rendering, and keep accessible heading names. Supporting copy waits for a heading on downward entry; upward entry follows viewport order. Hero title/subtitle/date/image use an ordered timeline. Other headings, copy, actions and image groups keep scoped independent triggers with route/media cleanup. Sticky-card targets use live viewport bounds as well as document flow coordinates. Functional catalogue/filter/dialog content is excluded from decorative reveal. Reduced motion exposes completed content.

The owner’s [Pinterest envelope reference](https://au.pinterest.com/pin/624944885834148658/) was inspected in local Edge video frames on 2026-10-29. The flap folds first, the card rises above the front panel, then remains readable before the page fades in. Entry width is bounded by viewport height as well as width. Generated transparent PNG paper chains replace the intermediate ribbon bows, and painted sprite ornaments replace vector doodles. The butterfly uses two CSS background halves of the same PNG with wing pivots at the body. A separately generated flower sprig sways above the bouquet while its wrapper drifts gently; this does not claim that every flower in the original raster is individually rigged. Lower ornaments have their own composition. Bubble-shaped CSS masks shape the section backgrounds without clipping content or controls. Mobile layouts use one top chain and shorter section/hero spacing; sprite cells retain square aspect ratios. A compact calendar and address note share the event composition beside its date/time and light-top dress preference. The address is now Abaya 89 (large hall), corrected by the owner. Coloured fields remain; supplementary page tops use smaller chains. The Canvas cursor trail is one stroke with palette interpolation.

The combined date/venue and RSVP wrapper and personal-story list use CSS sticky stacks without scaling or changing card-root opacity. The next card slides over the previous in native scroll, with automatic reversal. The venue keeps its shaped colour field. RSVP uses an actual SVG with two paths sharing the same top curve: an opaque paper backing extending downward, and a yellow bubble above it. The stack clips the extended backing at its own bounds with overflow: clip, which preserves document sticky behavior. A measured .stack-tail supplies real document-flow travel after RSVP, while its sticky top shifts upward by the SVG top-curve clearance. This lets the yellow wave fully cover the still-pinned venue. A padding-only tail would be excluded from sticky containing-block limits. Resize/media cleanup removes the measured variables, and tall-card/reduced-motion layouts omit the tail. The backing hides the venue below the yellow lower curve without painting a rectangle above the yellow upper curve. Personal-card backgrounds stay opaque. A ResizeObserver and viewport resize check disable sticky stacking when any card is too tall. Focus handling scrolls a covered card into a usable position. Reduced motion uses ordinary document flow. The empty wish feed has a stack container for future real `.stack-card` records; no sample wishes are generated. The owner's local reference notes remain in `рефы/Scroll-and-lettering-notes.txt`.

Music uses one control. AudioContext attempts resume on mount and retries on a trusted pointer/activation-key gesture when blocked; actual context state drives the button. Explicit pause prevents subsequent gesture retries until the button resumes audio. Listener/interval/context cleanup is tied to the component lifecycle. Browser autoplay permission is conditional ([MDN](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay)). There is no separate animation toggle. The envelope button explicitly retains opacity 1 when disabled during opening; its group stacks above the invitation line, and the card has opaque paper fill and 18px corners.

Generated illustration and audio origins are recorded in [asset provenance](invitation/public/art/PROVENANCE.md). The owner-specified cream/lavender palette, handmade ornaments, glass controls, airy composition and absence of a hero CTA override generic marketing-page inspector preferences. Automated style heuristics can misclassify transformed text, the calendar table and the route button; actual screenshots and interaction checks are the acceptance evidence, not a blanket claim that every heuristic passed.

## Deferred alternative: Payload with PostgreSQL

On 2026-10-27 the owner asked to record Payload with PostgreSQL as an available alternative only. The current recommendation above remains unchanged; this is not authorization to install Payload, migrate data or replace the architecture.

Payload provides a configurable administrator interface, authentication, access control and APIs, and officially supports PostgreSQL. It could reduce custom content-management UI work and support later reuse. Guest browser ownership, wish editing permissions and transactional gift reservation behavior would still require project-specific implementation and tests.

Payload requires a server runtime compatible with its Next.js deployment; it cannot run on static GitHub Pages. Adoption would require separate hosting for Payload or moving the combined application to suitable hosting, plus database and persistent image storage. A complete zero-cost deployment and its operating limits have not been validated. Reconsider only after checking these costs, hosting compatibility and maintenance implications; update this architecture and related documents if adoption is later decided. PostgreSQL is already part of the current Supabase recommendation, so the main alternative is the administrator/backend layer.

Official references reviewed during the discussion: [Payload overview](https://payloadcms.com/docs/getting-started/what-is-payload), [PostgreSQL adapter](https://payloadcms.com/docs/database/postgres), and [deployment requirements](https://payloadcms.com/docs/production/deployment).

## Planned code responsibilities

- `src/app/`: application initialization, navigation and session coordination.
- `src/features/invitation/`, `personal/`, `wishes/`, `wishlist/`: page-specific behavior and presentation.
- `src/features/admin/`: authenticated content forms and separate attendance/reservation tables.
- `src/components/`: genuinely shared fields, feedback and dialog behavior; visual components after design agreement.
- `src/data/`: typed Supabase access functions and response mapping; no database calls scattered through rendering components.
- `src/styles/`: shared foundations and, after approval, visual tokens.
- `supabase/migrations/`: schema, constraints, access policies and narrowly scoped database functions; no production records.

Wishlist cards use a stretched details button with separate sibling reservation/shop controls, avoiding nested buttons. A shared reservation form appears only after reservation intent, inline in the catalogue or in details; failures preserve input without implying persistence. The filter is a permanently visible, unfilled region in normal flow: category/currency/upper-budget selects, inclusive lower-budget tags, two price-order toggles and reset. There are no disclosure or scroll-collapse listeners. Optional shop metadata renders actual links when supplied; missing URLs leave a disabled «В магазин» action. Categories remain filter metadata. Full descriptions appear on catalogue cards, grouped with title and price; the grid equalizes closed content heights while leaving remaining space below the grouped content. A local ResizeObserver measures intrinsic image, text-child and action sizes, applying a shared minimum only to .gift-layout. The inline reservation lives outside that layout, so it grows only its own article. Measurements run on the next animation frame and avoid reading a stretched content box as its intrinsic height, preventing growth feedback. Resizing/filtering recomputes the baseline; cleanup disconnects observers and cancels pending frames. Shop is the left secondary action and reservation the right primary action. Optional image arrays support selectable detail photos and an optional note uses native details/summary with a caret. Details initially hide the name form, which opens only on reservation intent with accessible placeholder-based naming. Public availability determines the reservation button label and disabled grey state; synthetic fixtures cover occupied gifts without fabricating live reservations.

The memory page now has one introductory script heading, a form/feed composition with a quiet ordinary feed label, and a compact media-group action. No decorative plane or repeated script headings remain. Personal preference values, story-card titles and gift-dialog titles use Nunito. Calendar year/month share script styling, while the calendar caption and displayed city are removed. The time badge is a single reveal target, so its fill and text share opacity/translation. The heart note uses a complete rounded rectangle. Two lower butterflies reuse the existing wing component with distinct placement, pointer-events disabled and reduced-motion fallback. Contact/personal navigation reuse HandUnderline. Reservation-input focus reinforces only its underline, with a forced-colour outline fallback and a minimum 16px mobile font.

The contact action is a plain direct link to https://t.me/ADelhi; only the missing media-group link retains a notice dialog. Primary/secondary action styles are centralized in the shared button classes.

## Data and permissions

| Planned record | Contents | Access |
| --- | --- | --- |
| `site_content` | Structured editable texts, event details, contact and Telegram links, conversion rate/date | Public read of published fields; admin write |
| `personal_entries` | Owner-provided stories, captions, image references, order | Public read of published entries; admin write |
| `gifts` | Public catalog fields and publication state | Public published read; admin write |
| `attendance` | Browser owner ID, guest name, yes/no, timestamps | Submitter insert through validated operation; admin read/correct; no guest update |
| `wishes` | Owner ID, public name/text, timestamps | Public projection; author update; admin update/delete |
| `reservations` | Gift ID, owner ID, private guest name, timestamp | Validated claim/cancel operations; admin private read/correct |
| `admin_members` | Explicit administrator user IDs | Privileged setup only; no client self-assignment |

Public reads must expose only intended columns. Never publish reservation names or ownership identifiers through catalog payloads, views or error messages. Return public gift availability and a scoped own-reservation response separately from private reservation records. The reservations table is the surprise-sensitive location; the administrator reservation section displays it. No gift-association data belongs in Markdown or repository files.

Use a database unique constraint on reserved gift ID and a transactional claim operation to prevent double reservation. Cancellation checks the authenticated owner ID inside the database operation. Reject malformed values and invalid gifts on the backend. Use plain text for guest wishes; never render guest HTML. Record limits and enforce them consistently on the client and backend.

Enable row-level security on exposed tables. Audit view execution permissions and any security-definer function, its search path and grants; avoid elevated functions where policies suffice. Public availability endpoints must not bypass privacy accidentally. A hidden admin page is not authorization. Derive admin rights from protected membership, not client-controlled metadata. Privileged service keys stay outside the client build and repository; only publishable client configuration is shipped.

## Registration-free ownership

Create an anonymous Supabase Auth session when a guest first needs to submit or manage data. Retain the session in the browser using the supported client persistence mechanism. The server-issued user ID establishes ownership for database policies; IP and guest names do not. This is technical authentication without a guest registration form, email or identity verification.

The session is specific to browser storage and site origin. Private mode, cleared storage, a different browser/device or a domain change may lose access. Tell guests to contact the owner for corrections; do not offer unauthenticated ownership recovery by name. Losing a session does not delete the stored record. Attendance duplicate handling is best effort per session, not verified per human.

Use GitHub OAuth through Supabase for the administrator. Redirect credential entry to GitHub; do not collect passwords on Pages, whose documentation discourages sensitive transactions such as sending passwords. Allow only the explicitly provisioned owner user ID in protected administrator membership; successful GitHub sign-in alone must not grant admin rights. Configure exact callback/redirect URLs and test them with hash routing and the repository base path. Keep OAuth client secrets in Supabase provider configuration, never the browser bundle. Document account recovery through the identity provider and administrator reprovisioning before handover. An administrator must not silently inherit guest-only permissions or vice versa.

Public links can be forwarded. Anonymous writes need basic abuse controls: validate inputs, constrain text size, use submission throttling and evaluate the provider's recommended CAPTCHA protections. Select a free compatible challenge only if necessary; it must not add guest registration. Measure the chosen provider's rate limits against guests who may share the venue's network. Anonymous-account cleanup and database export must be documented before retirement.

## Content and media

Store editable content in the database so admin updates do not require a rebuild. Keep implementation-owned illustrations and approved static assets in the repository where appropriate. Use Storage only for administrator-managed site and gift images, with restricted upload/delete rights, validated image types and size limits, and optimized display versions. Guest photographs and videos are exclusively in Telegram. No backend Telegram integration is needed.

Validate shop/contact/Telegram links as allowed web links rather than executable schemes. Owner-provided content is not automatically safe HTML. Do not expose editor internals or drafts in public responses.

## Planned verification and tooling

The draft configures strict TypeScript, ESLint, Prettier, Vitest and production build scripts, with `.github/workflows/invitation-checks.yml`. Unit tests cover typography, contextual routes, gift filtering and refusal to report persistence without a backend. Browser layout checks use synthetic inputs and local Edge/Playwright. The source app does not load real guest data. Local verification results and limits are recorded in README; the remote CI workflow is not claimed to have run. The backend scenarios below remain planned. Lifecycle, risk-based selection, repair and reporting rules are authoritative in AGENTS.md. There is no code coverage percentage target.

Vitest and Playwright are installed. The runtime-safe `scripts/task.mjs` launcher runs tools using the selected Node executable; this avoids the old system Node being selected by Windows npm shims. All pages use the document scroller. Supplementary pages have a standalone fixed contextual return link, no dock or reserved footer viewport, and minimal end clearance. Browser checks cover content widths, contextual returns and final-content clearance. Database integration tests remain future work and must exercise real constraints and access policies in an isolated test target with synthetic data, independent guests A/B and an administrator. A local test backend is preferable where practical under the zero-budget constraint; do not silently create a paid or extra hosted project. Mocked network failures are useful for UI retry checks but do not replace real database permission/race checks.

| Planned area | Priority behavior to verify | Suitable check |
| --- | --- | --- |
| Attendance | Name and yes/no persist, are visible to admin only; guest updates are denied; failure retains input | Database integration and one browser flow |
| Wishes | Immediate public name/text; owner can edit; other guest cannot edit or delete; only admin deletes published records; raw markup is treated as text | Integration authorization checks and browser flow |
| Reservations | Two independent concurrent claims yield exactly one active reservation; only owner or authorized admin can cancel; public data and errors reveal no giver names or owner identifiers | Real concurrent database operations and direct API access tests |
| Browser ownership | Reload restores ownership in the same session; different browser cannot acquire rights by typing the same name; lost session shows general status without deleting stored records | Independent browser contexts with the real test backend |
| Admin | Sign-in alone does not grant administrator membership; guests cannot change content or grant themselves rights; approved edits reach public views | Direct API denial checks and admin browser flow |
| Retry and repeated actions | Repeated click or retry after an ambiguous network result does not silently create duplicate records; a known reservation conflict has a clear outcome | Persistence integration and controlled failure browser checks |
| Currency and filters | KZT/RUB conversion direction, display rounding, budget boundaries and invalid/missing-rate fallback | Focused logic tests |
| Navigation and Telegram | Direct entry/reload, contextual return, actual deployment base path and correct external group link | Browser smoke checks; live link check at launch |

For ambiguous retries, choose and document an appropriate operation identifier or equivalent server-side duplicate guard when implementing writes. This protects one repeated operation; it does not introduce verified identity or a guarantee against a human responding from another device. Validate repeated submissions alongside the user-visible result rather than relying on disabling a button alone.

Use manual browser inspection for agreed appearance, narrow phones and desktop, long Russian names/text, keyboard focus, floating return overlap, reduced motion and loading/empty/failure/saved-success states. Add automation only where useful for stable critical behavior. Production smoke checks must be non-destructive; keep write/mutation tests in the isolated environment. Verify real regional access and the confirmed external Telegram destination before launch.

Start with responsive appropriately compressed images, lazy loading below the fold and on-demand admin code; measure the actual build and page before selecting numeric performance budgets. No performance score is claimed now.
